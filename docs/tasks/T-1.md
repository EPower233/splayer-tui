## 结论（等用户试听后定稿）

**能。** SPlayer-Next 的音频引擎不用改源码，靠三个替身 crate 就能当普通 Rust 库用，构建时间也不是问题。

| 项目 | 结果 |
|---|---|
| 原样带 NAPI，干净 debug 构建 | 43.6 s |
| 替身版，干净 debug 构建 | 37.2 s |
| 替身版，改一行后增量构建 | 3.1～3.8 s |
| 替身版，干净 release 构建（LTO） | 1 分 21 秒 |
| release 版程序体积（含静态 FFmpeg） | 10.2 MB |

机器：Windows，Rust 1.95.0，MSVC。

对正式实现的影响：

1. **`splayer-audio` 沿用替身做法**：引擎源码保持和上游一致，同步上游基本就是覆盖目录。替身的接口要从"够实验用"收紧成正式代码。
2. **集成约束**：`stop()` 这类同步方法可能销毁 HTTP 流内部的 tokio 运行时，不能在异步上下文里调用，否则 panic。适配层要把它们放到阻塞线程上。
3. **ADR 0003 要改**：引擎依赖的 reqwest 0.13 默认用 aws-lc-rs，"只用 ring"做不到。改成全项目统一用 aws-lc-rs，fork ncm-api-rs 时把 reqwest 升到 0.13。
4. **Windows 构建环境**：有 `CC`/`CXX` 环境变量、或者 PATH 上是 msys2 的 libclang 时，要按上面的命令构建。要写进开发文档。

还没验证：人耳试听；Linux / X220（缺 `libpipewire-0.3-dev`、`libpulse-dev`）；网易云 CDN 的真实地址（T-2）。
