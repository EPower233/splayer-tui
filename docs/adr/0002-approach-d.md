# 0002. 用 Rust 独立实现，模块和类型对齐 SPlayer-Next（构法 D）

- 状态：已接受
- 日期：2026-11-08
- 决定人：E_Power（用户），claude-opus 提出

## 背景

这个 TUI 要做成 SPlayer-Next 的终端版，长期功能对齐 SPlayer-Next。SPlayer-Next 是 Electron + Vue + Rust：

- 业务逻辑约 4.6 万行 TS（主进程约 3 万、渲染进程约 1 万、共享类型约 5 千）；
- 核心的播放编排在渲染进程里；
- 已经有约 2 万行 Rust 原生模块：音频引擎、媒体控制、繁简转换、AutoMix 分析、录音采集；
- 上游几乎天天都有提交。

完整盘点见 `docs/scope.md` §1。

## 决定

用 Rust 独立实现，但做到下面三条：

1. **结构对齐**：模块划分、类型名和字段名照 SPlayer-Next 来（`shared/types`、`apis/<平台>`、`services/streaming/adapters`）。
2. **可追踪**：照着 SPlayer-Next 写的每个文件，开头注明 `对应 SPlayer-Next：<路径> @ <提交号>`，用脚本列出上游自上次同步以来改过的文件。
3. **可复用**：`domain`、`app` 和适配器 crate 不依赖终端库，接口只用普通的结构体和函数，SPlayer-Next 将来能加一层 NAPI 调用它们。

同时尽早和 SPlayer-Next 作者沟通方向。如果作者愿意从 SPlayer-Next 抽出一个共用的无界面内核（构法 C），再写一份 ADR 改方向。

## 考虑过的其他做法

- **A. Rust 重写，结构自定**：工作量和 D 一样，但以后追上游时要自己重新读代码找差异，也没法给 SPlayer-Next 用。
- **B. TUI 当 SPlayer-Next 的遥控器**：必须开着 Electron，失去在终端里轻量运行的意义；而且核心逻辑在渲染进程，要上游大改才能开放出来。
- **C. 和上游一起抽出 Node 内核**：功能和上游同源，但要上游愿意做一次大重构，主动权不在我们；TUI 还要带 Node 运行时。

## 后果

- 能单独运行，轻量，X220 和 SSH 都跑得动。
- 工作量大，要长期跟进上游；文件头的对应关系能让跟进变成"按差异改"。
- 自由度低一些：SPlayer-Next 的数据结构在终端里不顺手的，也先照着用。
- 怎么发现这个决定错了：如果对齐的规矩让进度明显变慢，又看不到被上游采用的可能，就重新评估 A。
