## 1. 产品一页纸（开工时搬进 `docs/spec/product.md`）

- **是什么**：在终端里跑的网易云音乐播放器，布局和手感像 SPlayer，长相和交互是 TUI 的。
- **给谁用**：习惯 SPlayer 或网易云、又常待在终端里的人，包括 rice 过的 Linux 桌面、SSH 到的机器、跑不动 Electron 的老电脑。
- **范围更新（2026-11-08）**：这个 TUI 要做成 SPlayer-Next 的终端版，长期目标是功能对齐 Next，不只做网易云。构法、分期和对现有计划的影响见 [scope.md](scope.md)。下面的 v0.1 只是第一期，并且领域模型从第一天就要支持多来源。
- **v0.1 做**：本地文件夹来源；扫码登录；首页；我喜欢的音乐、创建/收藏的歌单、每日推荐、私人漫游/心动模式、搜索；播放、队列、喜欢；逐字歌词（可关）和翻译；全屏播放页；封面取色主题；系统媒体控制（Windows SMTC / Linux MPRIS）；只支持「现代」终端档位。
- **v0.1 不做**：评论、QQ 音乐/酷狗、Navidrome/Jellyfin、本地曲库、下载、云盘上传、LX 音源插件、后台守护进程、「兼容」终端档位、图形界面版。
- **怎么算成功**：你在 Windows Terminal 和 X220 上能拿它代替 SPlayer 日常听歌一周；列表和歌词在这两个终端里不错位。

## 2. 架构：一个"播放器大脑"，前端可以换

用 Cargo workspace，每一层是一个 crate。**依赖只能往里指**：界面层能用大脑，大脑不知道界面的存在。用 crate 拆的好处是，这条规则由 Cargo 本身强制：内层的 `Cargo.toml` 里没写外层，代码就引用不到，不需要另写检查。

```
crates/
  domain/    纯规则，没有网络和文件：歌曲/歌单类型、队列和播放模式、
             歌词解析（LRC、网易逐字 YRC、翻译）与当前行/当前字计算、封面取色生成配色
  app/       播放器大脑：接收命令（播放、暂停、下一首、喜欢……），发出事件
             （状态变了、进度、换歌、歌词行）。需要外部能力时只调用四个接口：
             音乐来源、音频输出、系统媒体控制、本地存储
  netease/   网易云接口，实现"音乐来源"。基于 SPlayer-Dev/ncm-api-rs，见 §3
  audio/     音频引擎，实现"音频输出"。SPlayer-Next 的 audio-engine 或 rodio，见 §3
  mediactl/  系统媒体控制。先用现成的 souvlaki 库，SPlayer 的 media-ctrl 作参考
  store/     配置（TOML）、登录会话、缓存目录
  tui/       终端界面（ratatui + crossterm）：只读大脑给的快照来画，按键翻译成命令；
             「终端能力」结构（档位、模糊宽度、图片协议、图标集、透明/实底）也在这里
bin/splayer-tui/  把上面这些接起来的程序入口
```

**为什么这样分，代价是什么**：
- 界面不直接碰网络和音频，以后做 GPUI 或 Flutter 版时，大脑和下面几层原样复用，只换 `tui/`。
- 大脑和界面之间只传命令和事件。以后要做"关掉终端还在放歌"的后台进程，只要在两者中间插一个本地 socket，界面代码基本不动。
- 四个接口可以用假的实现替换，所以播放逻辑能在 CI 里测试，不需要网络和声卡。
- 代价：开头要多建几个 crate、写四个接口定义。只在这四个边界上写接口，内部不为"以后可能"抽象（工具包 §3.5）。

## 3. 拼装清单：每块用谁的

本项目用 AGPL-3.0（因为要用 SPlayer-Next 的代码）。下面每个来源的许可证都能并进 AGPL-3.0 项目。源码都已浅克隆到本机，不用重新下载。

| 部件 | 用谁的 | 许可证 | 怎么拿 | 要补什么 |
|---|---|---|---|---|
| 网易云接口 | [SPlayer-Dev/ncm-api-rs](https://github.com/SPlayer-Dev/ncm-api-rs)：SPlayer 团队自己的 Rust SDK，382 个接口，tokio + reqwest | WTFPL | 复制进 `crates/netease` 自己维护 | 它 2026-04 后没再更新。SPlayer-Next 9 月以后在 TS 里加的两样要移植过来：xeapi（`song_url` 要用）和易盾 v3 实时 token（`like` 要用），现在两版 Rust SDK 都只有一个写死的 token。CNMPlayer 维护着它的一个分支（改用 compio 运行时），里面 7 个月的修复可以对照着挑。v0.1 用到的约 15 个接口加上强类型的返回结构，参考 pigma 的 `ncm-api/model` |
| 音频引擎 | 首选 SPlayer-Next 的 `native/audio-engine`：FFmpeg 解码、交叉淡入、均衡器、变速、FFT、WASAPI 独占；备选 rodio + symphonia + stream-download：纯 Rust，CNMPlayer、pigma、ypm 都在用 | AGPL-3.0（FFmpeg 封装 ffmpeg-audio 是 GPL-3.0）；备选 MIT / Apache | 实验 1 决定。首选就复制进 `crates/audio`，删掉 `src/bindings/` | 首选的风险是编译时静态构建 FFmpeg，要先量时间 |

**拼装的规矩**（防止拼成一锅杂烩）：
- **只用一个异步运行时：tokio。** CNMPlayer 的代码跑在 compio 上，只借它的修复和思路，不原样搬。
- **整块拿，放在我们的四个接口后面**，不从各处抠零碎片段。
- **能当依赖就当依赖，必须改才复制。** 复制来的代码单独放一个目录，在 `THIRD_PARTY.md` 里记下来源仓库、提交号和许可证，以后上游更新了能对比着同步。
- **版本钉死**（学 Yokaze）。新加一个依赖先查许可证，没有许可证的一律不用。

## 4.5 性能：先定准绳，再优化（工具包 §6.5）

**准绳机器是 X220**：它是手上最弱的机器，在它上面流畅才算数，在这台 Windows 上测的不算。终端模拟器本身也要花 CPU 去画，所以每次测量都记下用的是哪个终端。

**初定的预算**（实验后再调）：

| 场景 | 预算 |
|---|---|
| 播放中、界面不动 | CPU < 1%（单核）；往终端写的数据接近 0，只有每秒一次进度更新 |
| 全屏播放页（逐字歌词 + 频谱） | CPU < 5%；往终端写 < 50 KB/s |
| 常驻内存 | < 60 MB，封面缓存有上限 |
| 启动到第一帧 | < 300 ms |
| 按键到画面变化 | 一帧之内 |
| 点歌到出声 / seek | < 1 s / < 300 ms（网络正常时） |
| 音频不断 | 故意把界面卡住 1 秒，声音不断 |

**怎么量**：在伪终端里跑一段固定脚本（比如在全屏播放页停 60 秒），记 CPU 时间、内存峰值和写给终端的字节数；用工具包的 `bench-ab.sh` 和基线提交交替跑，取中位数，结果记进 `docs/experiments.md`。单帧渲染耗时另用 criterion 基准测（主界面、全屏页，200×60）。

**决定性能的设计规矩**：
- **有事才重画**：按键、状态变了、歌词唱到下一个字，或者频谱在动，才画。不搞固定 60 帧刷新。
- **看不见就不算**（照搬 SPlayer 的内存纪律）：频谱这类高频数据，只在对应画面显示时才算、才推送。
- **控制输出字节**：ratatui 只写变化的格子，不做整屏动画；用"同步输出"模式（DEC 2026）避免画面撕裂。
- **封面只传一次**：图片按尺寸缩好缓存起来，换歌或改窗口大小时才重新发给终端。
- **长列表只画看得见的行**：967 首的歌单、3469 首的队列都一样。列表数据共享，不每帧复制。
- **音频和界面隔离**：解码和输出在独立线程，带缓冲；网络和磁盘走异步；封面解码放后台线程。界面卡住不影响出声。
- **大数据只留当前这首**：歌词、封面原图这类大数据只留当前曲目，所有缓存都要有淘汰规则（同 SPlayer）。

### 懒加载：用到才做

**启动**
- **先画缓存，再联网**：直接用上次退出时存的快照画出侧栏、上次打开的页面和播放栏。登录校验、刷新歌单都放到第一帧之后在后台做，所以网慢、断网也能秒开。
- **音频设备第一次播放时才打开**；系统媒体控制在第一帧之后才注册。
- **终端探测结果按终端缓存**：图片协议、背景色、字符宽度这三项，每项都要和终端来回问答一次，SSH 下更慢。按 `TERM` / `TERM_PROGRAM` 记下结果，下次启动直接用；用户要求时再重测。

**数据**
- **侧栏**：只拉歌单名和封面地址，点开歌单才拉曲目。
- **大歌单**（比如 967 首）：先拉第一屏用得到的曲目详情，剩下的在后台分批补齐，滚到哪先补哪。拉过的列表存在本地，下次打开先显示缓存，再按歌单的更新时间判断要不要重拉。
- **喜欢列表**：只拉 ID，一个请求，用来画 ♥。
- **每日推荐、私人漫游这类页面**：第一次打开才拉。每日推荐缓存到当天更新为止。
- **歌词**：换歌时才拉，原文、翻译、音译是同一个请求。
- **封面**：只拉看得见的行，并且按需要的尺寸拉。网易云的图片地址支持 `?param=宽y高`，SPlayer 也是这么用的。侧栏小图拉 32 像素，播放栏拉 64 像素，全屏页按终端实际像素拉，不下原图。取色用最小的那张。滚出屏幕的封面请求直接取消。
- **搜索**：输入停顿约 300 ms 才请求联想词，回车才做完整搜索；新请求发出时取消旧的。

**只在确定马上要用时提前拿**
- **下一首**（只在打开"预载下一首"时，默认照 SPlayer 是关的）：当前这首快放完时（比如还剩 20 秒）才去拿下一首的播放地址、开头一段音频、歌词和封面。不更早拿，因为播放地址会过期。SPlayer 也有这个开关。

### 其他优化

**画面**
- 进度条每秒最多重画一次，只写变了的格子。
- 逐字歌词按字推进：一个字唱完才重画，正在唱的那个字用半亮色过渡，不做字内渐变；每次只重画当前这一句。所以每秒的重画次数约等于每秒唱的字数，一般只有几次。关掉逐字后只在换句时重画。
- 暂停时频谱停算；频谱的柱数等于屏幕列数，算多了也画不出来。
- 列表行按显示宽度截好的文字缓存起来，窗口大小变了才重算。

**网络**
- 整个程序只用一个 HTTP 客户端，接口、图片、音频共用连接池。
- 图片下载限并发，比如最多 4 个。
- 音频边下、边播、边存；拖进度时用 HTTP 范围请求，只下需要的那一段；开了歌曲缓存的话，播过的歌直接从本地播。

**内存和磁盘**
- 接口返回的原始 JSON 转成精简结构后立刻丢掉。ncm-api-rs 返回的是通用 JSON 对象，3469 首的队列原样留着会很占内存。
- 内存里的封面只留看得见的和正在播放的，有数量上限。磁盘缓存（音频、图片、列表各一份）都有容量上限，按最近使用淘汰。
- 队列和播放位置不每秒写盘：换歌和退出时写，平时最多 30 秒写一次。

**编译**
- 依赖只开需要的功能。全程只用一套 TLS 加密后端（ring），不被拖进第二套（Yokaze 的配置注释里专门防过这个）。
- 发布版开 LTO、`codegen-units = 1`、strip：体积更小、跑得更快，代价是发布构建慢一些。
- 开发时 FFmpeg 只构建一次，靠 target 目录和 CI 缓存复用。

- 产品一页纸、`AGENTS.md`、`docs/architecture.md`、技术栈 ADR，从工具包模板填。

  2. **网易云**：用 ncm-api-rs 扫码登录 → 拿到喜欢列表 → 拿到播放地址（看不补 xeapi 能不能拿到）→ 拿到逐字歌词和翻译，再用 amll-lyric 解析。
