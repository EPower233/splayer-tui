# 做给 SPlayer-Next 的 TUI：范围和构法（草案，2026-11-08）

起因：SPlayer-Next 不只是网易云播放器。如果这个 TUI 是"SPlayer-Next 的终端版"，就不能只做网易云。

## 1. SPlayer-Next 到底有多少东西

按 SPlayer-Next 源码（提交 a8716df）统计，不含测试：

| 部分 | 内容 | 行数 |
|---|---|---|
| **音乐来源** | 网易云（4.7k）、QQ 音乐（2.6k）、酷狗（2.4k）、公共歌词（0.7k）、MusicBrainz（0.2k） | 约 10.6k |
| | 流媒体服务器：Subsonic 家族（Navidrome / OpenSubsonic / Airsonic / Gonic / LMS）、Jellyfin、Emby | 2.7k |
| | 本地曲库：扫描、SQLite、CUE、本地歌词库、元信息编辑 | 约 3k |
| | 插件：自己的插件系统 + LX 音源脚本兼容；插件是 JS 脚本，带权限管理 | 3.9k |
| **播放** | 播放编排（队列、心动模式、私人 FM、换源重试）、音源选择、预载下一首 | 约 3k（在渲染进程） |
| | AutoMix 自动混音、歌曲缓存、播放进度上报 | 约 2.1k |
| **歌词** | 多来源、多格式（LRC / QRC / YRC / TTML / KRC）挑选、TTML 库、排除、繁简转换 | 约 1.4k |
| **其他功能** | 下载、云盘上传、评论、动态封面、听歌识曲、统计、Last.fm、听歌打卡、外部 API、MCP、AI 模型、更新 | 约 4.5k |
| **Electron 粘合** | 进程间通信、窗口、托盘、任务栏 | 5.3k（终端版不需要） |
| **共享类型** | `shared/types`：Track、Album、Artist、Playlist、歌词、平台、流媒体… | 4.8k |
| **界面** | Vue 组件和页面 | 28k（终端版本来就要重写） |
| **Rust 原生模块** | 音频引擎、媒体控制、繁简转换、AutoMix 分析、录音采集、任务栏 | 20.5k（大部分能直接用） |

**业务逻辑大约 4.6 万行 TS 要处理**（主进程约 3 万 + 渲染进程约 1 万 + 共享类型约 5 千）。

另外有两点：
- 主进程 306 个文件里，只有 70 个引用了 Electron；其余都是普通的 Node 代码。
- **播放编排、音源选择、歌词挑选这些核心逻辑在渲染进程（Vue 那一侧）**，不在主进程。渲染进程和主进程之间有 31 组、约 218 个调用。

上游还在高频更新，几乎天天有提交。所以不管怎么做，"跟上 Next"都是一件长期的事。

## 2. 四种构法

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A. 全部用 Rust 重写** | 照 Next 的模块，一个个用 Rust 写一遍 | 单个程序、省内存、启动快，X220 和 SSH 都跑得动 | 约 4.6 万行要重写，而且要一直追 Next 的新功能。插件是 JS，要嵌一个 JS 引擎，实现同一套插件接口 |
| **B. TUI 当 Next 的遥控器** | Next 本体（Electron）开着，TUI 通过本地接口操作它 | 功能自动和 Next 一样 | 必须开着 Electron（几百 MB），失去在终端里轻量运行的意义。现有外部接口只能控制播放；核心逻辑在渲染进程，要上游大改才能开放出来 |
| **C. 从 Next 抽出一个无界面内核（Node）** | 把主进程那 236 个不依赖 Electron 的文件，加上渲染进程的播放编排，抽成纯 Node 的后台进程。Electron 界面和 TUI 都连它 | 和上游同一份代码，功能一起长；TUI 不需要 Chromium | 要上游愿意做一次大重构，主动权不在我们。TUI 要带 Node 运行时（几十到一百多 MB），比纯 Rust 重 |
| **D. Rust 内核，往上游靠拢**（A 的长期版） | 按 A 用 Rust 写，但模块划分、类型、目录都对齐 Next（`shared/types`、`apis/<平台>`、`streaming/adapters`），写成 Next 也能通过 NAPI 调用的库 | TUI 轻量。Next 本来就在把东西往 Rust 搬（音频引擎、媒体控制、繁简转换、AutoMix、录音采集都已经是 Rust），这些库有机会被上游收进去，变成两边共用，减轻长期追赶的负担 | 工作量和 A 一样大；"上游会收"只是有可能 |

**建议 D，并且尽早和 SPlayer-Next 作者（imsyy）聊一次方向。** 如果他愿意走 C，就改走 C。

### A 和 D 到底差在哪

两者写的都是 Rust，第 1 期的代码九成看起来一样。差别在三条规矩：

| | A | D |
|---|---|---|
| **结构** | 怎么分模块、类型叫什么，我们自己定 | 照 Next 来：Track、Album 这些类型的字段名和 Next 的 `shared/types` 一致；网易云接口一个 Next 模块对应一个 Rust 文件（比如 `apis/netease/modules/song_url.ts` 对应 `netease/src/modules/song_url.rs`） |
| **跟进上游** | Next 改了什么，要自己重新读代码去发现 | 每个 Rust 文件开头记下它对应的 Next 文件和提交号。一个脚本列出"自上次同步以来，Next 改过哪些文件"，就知道该改哪些 Rust 文件 |
| **能不能给 Next 用** | 不考虑 | 内核库不依赖任何终端界面的东西，接口只用普通的结构体和函数，这样 Next 可以像包装现在的音频引擎那样，加一层 NAPI 直接调用 |

**代价**：D 开头要多守这几条规矩，自由度也低一些：Next 的数据结构在终端里不顺手，也得先照着用。

**好处**：
- 就算上游永远不收这些库，单是"知道该同步哪里"这一条，就能让长期追赶 Next 省很多力气；
- 万一上游愿意收，这些库可以直接给 Next 用。

所以对"做给 SPlayer-Next"这个目标来说，D 就是"按这个目标做对了的 A"。

## 3. 对现有计划的影响

- **领域模型从第一天就是多来源的**：直接照搬 Next 的 `shared/types`，比如 Track 带 `source` 字段，平台有 netease / qqmusic / kugou，流媒体分 Subsonic / Jellyfin / Emby，再加本地和插件。
- **"音乐来源"接口照 Next 的分法设计**：在线平台、流媒体服务器、本地曲库、插件四类，播放器大脑不知道具体是哪家。
- **第一个打通的路径（walking skeleton）改成"本地文件夹"来源**：不用登录、不用联网，CI 里能稳定测试，最适合先把多来源接口打通。网易云紧跟其后。
- 拼装清单（plan.md §3）照旧，只是范围变大了。

## 4. 分期（对齐 Next 的功能）

| 期 | 内容 |
|---|---|
| 1 | 内核骨架 + 本地文件夹来源 + 网易云；界面主框架、全屏播放页、歌词、设置页 |
| 2 | 本地曲库完整版：扫描、SQLite、艺术家 / 专辑 / 文件夹页、CUE、元信息编辑；下载；歌曲缓存 |
| 3 | 流媒体服务器：Subsonic 家族、Jellyfin、Emby |
| 4 | QQ 音乐、酷狗；TTML 歌词库、更多歌词格式 |
| 5 | 插件（嵌 JS 引擎，兼容 Next 插件和 LX 脚本）；AutoMix |
| 6 | Last.fm、Discord、听歌打卡、外部 API / MCP、统计、听歌识曲、评论、动态封面（能做的部分） |

每一期结束都应该是一个能日常用的版本。
