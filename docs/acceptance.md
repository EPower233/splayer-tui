# 验收手册（给你用，2026-11-08）

这份文档写的是：我开工以后，每到一个节点交给你什么、你怎么自己检查、怎样才算通过。范围是第 1 期（v0.1），见 [plan.md](plan.md) 和 [scope.md](scope.md)。后面几期照同样的格式补。

## 0. 怎么用

每个里程碑结束时，我交一个**验收包**：

1. 一个合进 main 的提交，或者一个 tag；
2. 这份文档里对应那一节的清单，由我填好每一项的结果；
3. 证据：命令的原始输出、CI 链接、截图或录屏、测量数字。

你照着"你来验"那一栏，自己做一遍。**全部通过才算验收**。没通过的项，写进文末的验收记录，下一轮先修它。

任何一项**我没有验证到的，我会直接写"没验证"和原因**，不会写成"应该没问题"。

## 1. 开工前要先定的事

| 事项 | 卡住哪一步 | 你不定的话我的默认 |
|---|---|---|
| 构法：D（Rust 独立写，向上游靠拢），还是先找作者谈 C | M0 | 走 D |

| 谁来写、谁来审查（照工具包的 agents.md） | M0 | 我写；审查者由你指定 |

## 2. 每次交付都要满足的

每个合进 main 的提交，都必须满足下面这些。

| 要求 | 你怎么查 |
|---|---|
| `scripts/check.sh` 在最终那个提交上是绿的 | 自己跑 `bash scripts/check.sh`；PR 描述里也贴着输出 |
| CI 是绿的（Windows + Linux） | 点 PR 里的 CI 链接 |
| 一个任务一个 squash 提交，带 `Task:` 和 `Agent:` 尾注 | `git log --format='%h %s%n%b' main` |
| 任务卡写了验收命令和实际结果，还写了"哪些没验证" | 打开 `docs/tasks/T-编号.md` |
| 改了行为就有测试，放在能抓住它的最低一层 | 看 PR 的改动里有没有对应的测试 |
| 结构变了就更新 `docs/architecture.md`；做了取舍就有 ADR | 看 PR 改动 |
| 从别的项目复制的代码，在 `THIRD_PARTY.md` 里登记了来源仓库、提交号和许可证 | 打开 `THIRD_PARTY.md` |
| 新加的依赖查过许可证，没有许可证的一律不用 | 同上 |
| 按键冲突测试通过：每个窗口"全局 + 本窗口"没有重复 | `cargo test keymap` |
| 界面快照变了，PR 里写明为什么变 | `cargo insta review` 没有未审阅的快照 |
| 性能没有退步：和上一个基线比，CPU、内存、写给终端的字节数在预算内 | `docs/experiments.md` 里有本次的数字 |
| 登录凭据、Cookie 没有进仓库 | `git grep -i -E "MUSIC_U=|__csrf=" -- ':!*.md'` 没有结果（文档里提到这两个名字不算） |

我的承诺：

- 每个提交的证据都来自那个提交当时真实跑出来的结果，不事后补、不拆分重写历史；
- 失败就贴原始输出；
- 没有你的同意，不推远端、不发布、不删分支。

## 3. 各里程碑的验收

### M0 第 0 天：骨架和三个摸底实验

**交付物**
- 仓库骨架：git、钩子、`scripts/check.sh`、CI；`AGENTS.md`、`docs/architecture.md`、技术栈 ADR、`docs/spec/product.md`（产品一页纸）、空的 `THIRD_PARTY.md`。
- Cargo workspace：`domain`、`app`、`audio`、`netease`、`mediactl`、`store`、`tui` 几个 crate，先只有空壳，但依赖方向已经定好。
- `docs/experiments.md`：三个摸底实验的报告。每个实验都写清结论（能 / 不能）、数据、复现命令：
  1. 音频引擎去掉 NAPI 后能独立编译；能放一首本地 FLAC 和一个网络地址，并能 seek；干净构建和增量构建各要多久。
  2. 用 ncm-api-rs 扫码登录 → 拿到喜欢列表 → 拿到播放地址（不补 xeapi 能不能拿到）→ 拿到逐字歌词。
  3. ratatui 画出样稿骨架；中日韩字符和 emoji 对齐；彩色下划线；封面（含 kitty 下封面只上传一次）。
- X220 上的第一组性能基线：骨架空跑、带频谱时的 CPU 和写给终端的字节数。

**你来验**
1. 在一份干净的 clone 里跑 `bash scripts/setup-repo.sh`，再跑 `bash scripts/check.sh`，应该全绿。
2. 照 `docs/architecture.md` 里的"违规示例"，让 `domain` 引用 `tui`，改一行。`check.sh` 应该变红。这证明依赖方向真的由 Cargo 强制。
3. 推一个随手起名的分支，应该被钩子拒绝。
4. 打开 `docs/experiments.md`，挑一个实验，照它写的复现命令自己跑一遍，结果应该对得上。

**通过标准**
- 三个实验都有明确结论；"不能"的写明卡在哪、换什么方案。
- 构建时间和 X220 基线都有具体数字。
- 改一处代码后，相关检查 2 分钟内跑完；CI 全量 10 分钟内跑完。做不到要写明原因和对策（工具包 §6.4）。

## 4. 性能验收

准绳机器是 X220。预算见 [plan.md](plan.md) 4.5 节，这里摘出验收要看的几项：

| 场景 | 预算 |
|---|---|
| 播放中、界面不动 | CPU < 1%（单核）；几乎不往终端写数据 |
| 全屏播放页（逐字歌词 + 频谱） | CPU < 5%；往终端写 < 50 KB/s |
| 常驻内存 | < 60 MB |
| 启动到第一帧 | < 300 ms |
| 点歌到出声 / 拖进度 | < 1 s / < 300 ms（网络正常时） |
| 故意把界面卡住 1 秒 | 声音不断 |

**测法**：`scripts/bench.sh` 在伪终端里跑一段固定脚本，记录 CPU 时间、内存峰值和写给终端的字节数；用工具包的 `bench-ab.sh` 和基线提交交替跑，取中位数。结果追加进 `docs/experiments.md`，每次都写明用的是哪个终端。

**你怎么查**：打开 `docs/experiments.md`，最新一行要在预算内；也可以在 X220 上自己跑 `scripts/bench.sh`。
